# Phase 5B — ブラウザ完結の日本語解析：性能ベースライン

## 対象範囲と測定しないもの

`bun run bench:analysis` で、合成文書に対して以下の処理を計測する。

- `buildRuleContext`：Markdown・URL等のマスク、行分割、行先頭位置
- `runOwnRules(..., 'fast')`：高速ルール群
- `runOwnRules(..., 'deep')`：自前の詳細ルール群
- `runOwnRules(..., 'idle')`：文書全体ルール群

**この測定は、ブラウザ入力応答時間でも、Web Workerの往復時間でもない。**
textlintアダプター、DOM/CodeMirror描画、Workerの転送コスト、
ブラウザによるGCや実端末の体感は別のブラウザE2Eベンチで測定する。

## 入力と再現性

完全に決定論的な合成入力を使う（本物のユーザー文書は参照しない）。
長さはJavaScriptのUTF-16 code unit単位で厳密に指定する。

- 1,000 / 10,000 / 50,000 / 100,000 UTF-16 code units
- prose：通常の日本語文
- markdown：見出し・URL・コードフェンス
- repetition：冗長表現、接続詞、助詞句の反復
- long-sentence：長い文節（句点なしを想定）

通常のフル計測は2回ウォームアップ、5回計測。
最小・中央値・p95・p99・最大値を最近傍順位で算出する。
ただし5サンプルから得たp99は統計的に安定せず、
**「参考値」であることを明記する。** ベースラインを
比較する際は同一マシン・同一ブラウザ/runtime・同一条件を用いる。

`bun run bench:analysis` はJSONレポートをstdoutに出力する。
ユーザー文書は送信せず、CSV/JSONにも原文は含めない。

## CI品質ゲート

`bun run bench:smoke` では1,000文字と10,000文字の入力に限定し、
構造化された合成入力が実際の独自ルールを通して
例外なく処理されることを確認する。Vitestのユニットテストも
ワークロード生成器・パーセンタイル・UTF-16長を検証する。

共有GitHub Actionsの実行時間やGCは不安定なため、
**ms単位の固定しきい値ではCIを落とさない。**
性能回帰の定量ゲートは環境・計測手順・許容変動を固定してから追加する。

## 次の最適化候補

1. Worker内のRevisionごとにマスク・行索引を1回生成し、
   Fast/Deep/Idleで共有する（textlintとの境界を守る）。
2. 連続入力の最新Revisionだけを処理するようWorker Queueを統合。
3. 50k〜100k文書の長文ワークロードでメモリ・GC・入力遅延を検証。
4. 実ブラウザでp50/p95/p99、転送時間、First Lint、
   取り消されたRevisionのCPU浪費を計測。
5. 差分解析は、文書構造・引用・参照定義の前後依存を
   保持できる場合にだけ試験的に採用する。

データの移行・LLM・新たな外部API・永続保存機能は追加しない。
