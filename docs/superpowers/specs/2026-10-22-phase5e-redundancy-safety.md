# Phase 5E — 冗長表現の診断精度と置換安全性

## 背景と確認されたリスク

既存の `wording/redundancy` では次の機械的な置換提案が存在した。

- 「編集することができます」→「編集できます」：成立する例
- 「予約をすることができます」→「予約をできます」：不自然になる例
- 「変更をすることが可能です」→「変更をできます」：助詞が不自然になる例

このように末尾の文字列だけを差し替えても、直前の目的語や格助詞を
考慮できない。現状のブラウザ専用エンジンは係り受け解析を行わないため、
これらの候補をQuick Fixとして出すことは安全ではない。

また、「行ないます」という表記をそのまま例示する引用文に対しても
既存のSafe Fixが作用し得た。引用として忠実に保持すべき文章の
改変は望ましくない。

## 変更内容

1. `することができる`、`することができます`、
   `することが可能です` を **情報提供のみ**の診断へ変更。
   文章全体の助詞・活用を確認するよう案内する。
2. 意味変更リスクの低い「行なう→行う」などの
   明示的な表記修正はSafe Fixを維持する。
3. 「」・『』内の日本語例文、およびMarkdown blockquoteを
   執筆者の本文から除外する。既存のコード/URLマスクも維持する。
4. 同一ルール内で完全に同じ範囲を複数回診断しない。
   検出結果は文字位置の昇順に並べ、絵文字を含むUTF-16 offsetを守る。
   部分的に重なるが意味の異なる診断まで一律に消さない。

## デザイン上の判断

- **元文保持を優先**：不確かな箇所は診断のみ。
- 診断内容の重複は同一rule/spanに限定して除去。
  異なるルールが同じ文字に対して独立した有効な指摘をする可能性は残す。
- 正規表現と共有の引用マスクを利用し、形態素解析・AIは導入しない。
- 既存の `RuleProvider`、Rule ID、プリセット、保存スキーマを変えない。
- Safe Fixは必ず再Lintされる従来のFormatter検証フローを維持する。

## テスト

- 目的語の「を」を含む文でも不自然な置換を提案しない
- 引用中のSafe Fix適用を防止する
- 引用の前後にある通常本文は検出・変更できる
- emojiのUTF-16オフセット、複数ルール、重複範囲の安定性
- URL/HTMLコメント/Markdownコード/blockquoteを除外
- 既存の回帰コーパスに引用/助詞連携の例を追加
- TypeScript、全Vitest、Bunベンチマークsmoke、ViteとPagesを検証

合成コーパスの回帰結果は実文書のPrecisionの代替ではない。
