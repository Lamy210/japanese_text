# 業務文書レビューの7観点 — 段階的対応計画

## 方針
本ツールはブラウザ内・LLM不使用・非送信の静的校正を維持する。文章の意味・相手の知識・レビュー権限・発言者の事実関係は、本文だけで断言しない。ヒューリスティックは情報（info）レベル、原則として自動置換しない。

| 観点 | 既存機能・今回の対応 | 今後の対象 |
| --- | --- | --- |
| 1. 結論を先に | 現段階で意味的な結論判定は未対応 | 「回答/報告/相談」文書種別と結論欄を用いた任意の構成チェック |
| 2. 文のつながりと順序 | 文頭接続詞の反復・混在、段落密度は既存 | 逆接・並列の意味検証はLLMなしでは断定不可。選択肢の見出し・番号抜けを構造検査 |
| 3. 引用と回答 | 今回：Markdown引用の半角スペース不足を検出 | 前後の空行・質問引用の有無を文書種別付きで判定。原質問の全文性は原文がないと判定不可 |
| 4. 簡潔さ | 既存：冗長表現・同語反復・名詞化動詞。今回：クッション言葉の要確認 | 文書内同義重複の評価、不要な経緯の手動レビュー |
| 5. 表記と体裁 | 既存：用語、文体、誤表記、Markdown見出しと参照 | 敬称混在、宛名・締め前の改行、技術プレースホルダー表記 |
| 6. 議事録 | 未対応 | 文書種別「議事録」向け参加者・決定事項・担当者・未決事項テンプレートと欠落検出 |
| 7. 進め方・姿勢 | 今回：本文表現の一部のみ | レビュー履歴・メンション確認は文書Lintではなくチェックリスト/ワークフローで実装 |

## 非機能要件・検証
- 既存 Fast rule provider とプロファイルの設計に従う。
- コードブロック、引用された例、URLを極力除外する。UTF-16オフセットを維持する。
- 自動修正による意味の改変をしない。既存 Formatter の Safe Fix 契約を保持する。
- 誤検出・見逃しを共に計測できるよう、positive/negative/Markdown code/Unicode の回帰ケースを追加する。
- 本文送信や外部API、CIワークフローの追加は行わない。
- 次フェーズでは「回答」「社内連絡」「相談」「議事録」「資料」の文書種別別チェックリストを実装し、事実確認が必要な項目を機械判定と分離する。

### 受入条件
1. `>質問` を情報診断し、`> 質問` は診断しない。
2. コードブロック内の `>質問` を診断しない。
3. クッション言葉の診断に自動置換を付けない。
4. General / Technical / Strict では有効、Minimal では無効。
5. Bun の型チェック、テスト、ビルドが成功すること（実行できた環境で記録する）。
